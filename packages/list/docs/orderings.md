# List orderings across apps

One document for one class of defect ([rule](../../../AGENTS.md)): the
order of events when two apps write the collection `list` of a space.
It is here, in the package both apps write the list with, because the
rows are about the meeting of the two; what Emptio alone does to the
list is in Emptio's table[^emptio], the cycle and the loops in the host
package's[^host]. Today the second writer is Culina's hand-over
(`apps/culina/packages/app/src/shared-list/hand-over.ts`, offered on
the page of a shipped dish since 2026-11-24). The tests are in `apps/culina/packages/app/test/hand-over.test.ts`
and named as 'name'.

## What these tests do not prove

- The shared database is the memory store, except in the two-tab row,
  which runs two stores on one fake-indexeddb factory. The memory
  store's change is synchronous, so two changes cannot interleave; that
  the same holds in a browser's IndexedDB across real tabs is believed
  (readwrite transactions on one store are serialised) and not run.
- Emptio is not run here: its `addToList` is the same `planAdd` the
  tests call inside `localChange`. Its web screens are run against
  Culina's entries by the site e2e only.
- The storage is a memory stand-in with etags; the clock and the ids
  are injected.
- What a cook sees is checked by Culina's `e2e/hand-over.mjs` and the
  site e2e (`scripts/site-e2e.mjs`, Emptio showing Culina's entries
  and Undo leaving the one ticked there), in one browser profile, not
  across devices or with a storage.
