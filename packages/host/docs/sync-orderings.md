# Sync orderings

One document for one class of defect: what happens when things about
sync occur in an unlucky order. Each row is an ordering of events, the
behaviour that is intended, and the test that pins it. Whoever changes
the sync code looks here first; whoever fixes an ordering bug adds a
row ([Adding a row](#adding-a-row)). The mechanics are in
[spaces](spaces.md); this page does not repeat them.

Reading the last column:

- A test is named as `file` › 'name', exactly as in its `test('…')`
  call. Each was opened and its body checked against the row.
- **not pinned**: no test asserts it. The row says why it is believed to
  hold, or that it is not known.
- **not handled**: the code does not handle it. The row says what
  happens instead.
- **partly**: one half is pinned, the other is not; the row says which.

Where the files are: `cycle.test.ts`, `watch.test.ts`, `store.test.ts`,
`device.test.ts`, `seal.test.ts`, `github.test.ts` and `webdav.test.ts`
and `collection-sync.test.ts` (until 2026-11-20 Mixtura's
`stock-sync.test.ts`) are in `packages/host/test/`;
`stock-state.test.ts`, `stock-spaces.test.ts`, `stock-spaces-rules.test.ts` are in
`apps/mixtura/packages/app/test/`; `flows.test.ts` is in
`apps/domus/test/`.

## A change by the user while a cycle is running

| Ordering of events                                                                                       | Intended behaviour                                                                                                                                                                         | Pinned by                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The user puts one record and removes another after the cycle read the file and before its write finished | The change is merged over the plan's result and not lost; `syncedAt` and the etag are stored; the result says `pending: true`. The next cycle writes the change and says `pending: false`. | `cycle.test.ts` › 'a change made during a cycle is not lost and gives pending'                                                                                              |
| The same change arrives in a cycle that needs no write (the file already equals the plan)                | The same branch runs after the read: the change is kept and `pending` is true.                                                                                                             | not pinned. The hook of the test above fires only inside a write; the code after the write is shared.                                                                       |
| The write fails (conflict after the attempts, an error) while the user changes something                 | The change was made in the store at once; the failed cycle stores nothing, so the change stays and the next cycle sends it.                                                                | not pinned. 'a conflict every time gives conflict after the attempts and stores nothing' proves the store is untouched by a failed cycle, but makes no change meanwhile.    |
| The user changes something between two attempts after a conflict                                         | The next attempt reads the local state again, so the change goes into its write.                                                                                                           | not pinned. Holds by `syncCollection` reading the store at the top of each attempt.                                                                                         |
| The user changes a key during a cycle, and the file holds a later stamp for the same key                 | Newest wins: the file's record replaces the user's change, and nothing tells the person. The user's stamp was made without seeing that record.                                             | not pinned. By `mergeRecords`; the rule itself has its vectors in materia.                                                                                                  |
| Two changes by the user at the same moment                                                               | Each `changeRecords` is one atomic read-modify-write; neither is lost.                                                                                                                     | `store.test.ts` › 'parallel changeRecords calls do not lose each other' (memory and IndexedDB, ten calls in one page). Two tabs rely on IndexedDB transactions; not pinned. |
| The edit of a change throws (an unreadable clock)                                                        | Nothing is stored; the error reaches the caller.                                                                                                                                           | `cycle.test.ts` › 'an unreadable clock throws BadClock and changes nothing'; `store.test.ts` › 'a throwing fn changes nothing and the error reaches the caller'             |

## Two devices writing

| Ordering of events                                                                                     | Intended behaviour                                                                                                                                                              | Pinned by                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Both change different keys before either has synced                                                    | Both end with both changes.                                                                                                                                                     | `cycle.test.ts` › 'two devices converge after each made a change'                                                                                                                                                                                                                                              |
| One removes a key, the other syncs afterwards                                                          | The removal reaches the other device.                                                                                                                                           | `cycle.test.ts` › 'a removal on one device removes on the other'                                                                                                                                                                                                                                               |
| The other device writes between our read and our write                                                 | The write answers `conflict`; the cycle starts over from the read and converges.                                                                                                | `cycle.test.ts` › 'a conflict on write starts over and converges'                                                                                                                                                                                                                                              |
| The other device keeps winning (a storm)                                                               | After `attempts` (3) the result is `conflict`, and local data is as it was.                                                                                                     | `cycle.test.ts` › 'a conflict every time gives conflict after the attempts and stores nothing'                                                                                                                                                                                                                 |
| The storm ends, and the next cycle runs                                                                | The next cycle succeeds; nothing was lost. [Spaces](spaces.md#limits) says so.                                                                                                  | not pinned. The tests end a conflict after one round, never after the attempts ran out.                                                                                                                                                                                                                        |
| Both devices change the same key before either has synced                                              | The later stamp wins as a whole record; the other change is lost.                                                                                                               | not pinned here. The rule is materia's; no hospes test makes two devices write one key.                                                                                                                                                                                                                        |
| Both devices create the file when there is none                                                        | Each writes with the condition "no file yet"; the second gets `conflict`, starts over, reads the file and merges.                                                               | partly. `github.test.ts` › '422: conflict with a condition, server without' (a write with `null` that meets 422 is `conflict`) and `webdav.test.ts` › 'write with an etag sends If-Match; with null sends If-None-Match: *' pin the adapter half. The cycle half, a first write that conflicts, is not pinned. |
| A device that made its own data joins a storage that already holds the file of the space               | The cycle merges both; the later stamp wins on both devices.                                                                                                                    | `flows.test.ts` › 'connect: a storage that already holds the file of this space is merged by the cycle'                                                                                                                                                                                                        |
| Two tabs of one device run a cycle at the same time                                                    | The etag decides the file, the store is atomic. One cycle may take the other's stored records for a change of the user and answer `pending: true`, which costs one extra cycle. | not pinned. By the code only.                                                                                                                                                                                                                                                                                  |
| Mixtura: one device marks stock, a second device with a loop reads it, marks it again, the first reads | Both devices end with the newest mark, and the screens are told that records changed.                                                                                           | `collection-sync.test.ts` › 'two devices converge on the stock of a shared space'                                                                                                                                                                                                                              |

## A file that cannot be read, and failures of the storage

| Ordering of events                                                                            | Intended behaviour                                                                                                                                                                                              | Pinned by                                                                                                                                                                                             |
| --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The file is sealed with another secret, or is not a sealed file at all                        | `wrong-key` or `not-sealed` is returned; the file is not overwritten; `syncedAt` stays unset.                                                                                                                   | `cycle.test.ts` › 'an unreadable remote file is not overwritten'                                                                                                                                      |
| The file of another collection is put in its place                                            | `wrong-key`, not overwritten (the collection is part of the sealed data).                                                                                                                                       | `cycle.test.ts` › 'a file of another collection put in its place is wrong-key, not overwritten'                                                                                                       |
| A valid seal holds a document of another space                                                | `other-space`, and no write follows.                                                                                                                                                                            | partly. `cycle.test.ts` › 'a file of another space inside a valid seal is other-space' asserts the failure only, not that nothing was written. The return comes before the write in `syncCollection`. |
| The file, or the document in it, is of a newer version                                        | `newer-version`, and no write follows.                                                                                                                                                                          | partly. `seal.test.ts` › 'a newer version is newer-version' pins the open; the cycle half is not pinned.                                                                                              |
| One byte of the ciphertext or the nonce is flipped (a damaged file)                           | `wrong-key`; a damaged file and a wrong secret cannot be told apart.                                                                                                                                            | `seal.test.ts` › 'a flipped ciphertext byte or nonce byte is wrong-key' (the cycle half is the first row of this table)                                                                               |
| The file decrypts but is no collection document                                               | `bad-document` with the parse error as detail; not overwritten.                                                                                                                                                 | partly. `seal.test.ts` › 'decrypted but not a collection document is bad-document with detail' pins the open; the cycle half is not pinned.                                                           |
| The storage is unreachable, refuses the token or blocks the page, on the read or on the write | The failure is returned as it came, with its detail; nothing is stored; `syncedAt` is unchanged.                                                                                                                | `cycle.test.ts` › 'adapter failures are returned unchanged'                                                                                                                                           |
| The same, in Mixtura, with local stock                                                        | The status says `failed`, the local stock stays; the first good cycle clears the failure.                                                                                                                       | `collection-sync.test.ts` › 'a failed cycle is told, keeps the local stock and is forgotten after a good one'                                                                                         |
| The remote write succeeded, then the local store throws (quota, a closed database)            | `syncCollection` rejects. The loop counts that as a failure; Mixtura turns it into `server`. The file has the data, local keeps its old etag and `syncedAt`; the next cycle repeats and finds nothing to write. | not pinned. Believed to hold because the merge is repeatable; no test makes the store throw in the last step.                                                                                         |
| The device or the page dies between the remote write and the local store                      | The same as the row above.                                                                                                                                                                                      | not pinned, and cannot be with these fakes ([below](#what-these-tests-do-not-prove)).                                                                                                                 |
| The storage type is one this build does not know                                              | The space shows `storage` as its failure and no loop runs.                                                                                                                                                      | `collection-sync.test.ts` › 'a storage this build does not know is told as such and no loop runs'                                                                                                     |

## Clocks

| Ordering of events                                                                                                                 | Intended behaviour                                                                                                                                                                                                                                                               | Pinned by                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The device clock is behind the newest stamp in the collection when the user changes or removes                                     | The stamp is the newest stamp plus one millisecond, so the change wins and an edit after a removal stays later than the marker.                                                                                                                                                  | `cycle.test.ts` › 'stamps are later than everything in the collection, even with a clock in the past'; `stock-state.test.ts` › 'a mark is stamped after everything in the collection, even with a clock that is behind'     |
| A record with a stamp ahead of this device's clock arrives by a cycle, then the user changes it                                    | The same rule: the arrived record is in the local collection, so the change is stamped after it.                                                                                                                                                                                 | not pinned. The tests above seed the local collection; none lets the record arrive through a cycle.                                                                                                                         |
| The clock gives no timestamp                                                                                                       | A cycle returns `bad-now` and stores nothing; a user change throws `BadClock` and changes nothing.                                                                                                                                                                               | `cycle.test.ts` › 'a bad clock is bad-now'; `cycle.test.ts` › 'an unreadable clock throws BadClock and changes nothing'                                                                                                     |
| A device is away for longer than the 90 days markers are kept, and others removed a record meanwhile                               | The returning device drops what the file lacks and it has not touched since `syncedAt` (listed in `expired`), and keeps what it edited after `syncedAt`.                                                                                                                         | `cycle.test.ts` › 'a device away longer than the horizon drops what was removed meanwhile, keeps what it edited'                                                                                                            |
| A device edited a record before leaving, never synced it, and another device removed that record meanwhile                         | The edit is newer than `syncedAt`, so the record is kept and comes back, and the removal is undone ([materia, limits](../../model/docs/sync.md#limits-of-this-version)).                                                                                                         | not pinned here. The test above has no removal of an edited record.                                                                                                                                                         |
| The user edits with the clock set behind `syncedAt`, and the next cycle meets a file whose `prunedBefore` is later than `syncedAt` | **Not handled.** The edit has a stamp not later than `syncedAt` and the file lacks the key, so the stale device rule takes it for a record removed elsewhere and drops it (`expired`). `nextStamp` protects the stamp; `syncedAt` is the raw clock ([spaces](spaces.md#limits)). | not handled, not pinned. Reproduced with a throw-away test that was not kept: syncedAt 10 January, clock set to 5 January, edit `y`, a later prune by another device; the cycle returned `expired: ['y']` and `y` was gone. |
| A device with a clock far ahead prunes removal markers early and writes a late `prunedBefore`                                      | Other devices whose `syncedAt` is earlier treat themselves as stale and drop what the file lacks; a record whose marker went early is dropped on a device that never saw the removal. Markers pruned early cannot be recovered.                                                  | not pinned. By the code of `planCollectionSync` and `pruneTombstones`.                                                                                                                                                      |
| A device's last cycle ran with a clock far ahead, which was then corrected                                                         | `syncedAt` is later than any `prunedBefore`, so the stale rule never fires there; a record removed elsewhere whose marker was pruned can come back with the next write.                                                                                                          | not pinned. By the code only; not run.                                                                                                                                                                                      |
| A device with a clock far ahead writes records                                                                                     | Its records win every conflict until the others have seen them; after that their changes are stamped later.                                                                                                                                                                      | not pinned here. A known limit of materia.                                                                                                                                                                                  |

## The loop: start, interval, poke, a request during a run, back-off, hidden page, offline, stop

| Ordering of events                                                | Intended behaviour                                                                                                                                                            | Pinned by                                                                                                                                                                                                                                               |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start                                                             | A cycle runs at once, then every interval (20 s; a given interval is used).                                                                                                   | `watch.test.ts` › 'runs now on start, then every interval (default 20 s)'; `watch.test.ts` › 'a given interval is used'                                                                                                                                 |
| Start twice; start after stop                                     | Twice starts once; after a stop it starts again.                                                                                                                              | `watch.test.ts` › 'start twice starts once; start after stop starts again'                                                                                                                                                                              |
| Stop                                                              | Timers are cancelled; nothing runs after.                                                                                                                                     | `watch.test.ts` › 'stop cancels the timers; nothing runs after'                                                                                                                                                                                         |
| Stop while a cycle is running                                     | The run finishes; no timer, poke or repeat follows.                                                                                                                           | `watch.test.ts` › 'stop during a run: the run finishes and nothing follows'                                                                                                                                                                             |
| Stop, then start again while the old run is still in flight       | The old run ends, runs once more for the remembered request, and the interval continues. No two runs overlap.                                                                 | not pinned. By the `running` and `again` flags; `started` is true again when the old run returns.                                                                                                                                                       |
| A tick, a signal or `syncNow()` arrives during a run              | Remembered; one cycle runs after the first, never two at once.                                                                                                                | `watch.test.ts` › 'never two cycles at once; a request during a run runs once after'                                                                                                                                                                    |
| Manual: start, interval, watch                                    | Nothing runs at the start, on an interval or on a watch signal; `poke`, `syncNow` and `runNow` still run a cycle.                                                             | `watch.test.ts` › 'manual: nothing at start, no interval, no watch; asked cycles still run'                                                                                                                                                             |
| `runNow()` during a run                                           | Waits for the run in flight and the one more it asks for; every waiter gets the result of that last cycle. Offline or stopped: false, nothing runs.                           | `watch.test.ts` › 'runNow resolves with the result of its cycle; during a run it waits for one more'; 'runNow offline runs nothing and says false'; `collection-sync.test.ts` › 'manual: no cycle until asked; syncSpace runs one and says how it went' |
| A watch signal arrives during a run                               | Remembered; one cycle runs after.                                                                                                                                             | `watch.test.ts` › 'a watch signal during a run is remembered and runs once after'                                                                                                                                                                       |
| Several pokes within 2 s                                          | Each push the cycle back; one cycle runs 2 s after the last.                                                                                                                  | `watch.test.ts` › 'poke waits 2 s and several pokes make one cycle'                                                                                                                                                                                     |
| A poke arrives, or its timer fires, during a run                  | The timer's cycle is remembered and runs after the run.                                                                                                                       | not pinned. By the same flag as the rows above.                                                                                                                                                                                                         |
| The result says `pending: true`                                   | Another cycle follows in 2 s.                                                                                                                                                 | `watch.test.ts` › 'a result with pending asks for another cycle in 2 s'                                                                                                                                                                                 |
| Runs fail                                                         | The interval doubles (40 s, 80 s, 160 s) up to 300 s; a success resets it.                                                                                                    | `watch.test.ts` › 'a failed run backs off by doubling up to 5 minutes; a success resets it'                                                                                                                                                             |
| The run throws                                                    | Counts as a failure; the loop goes on.                                                                                                                                        | `watch.test.ts` › 'a run that throws counts as a failure and the loop goes on'                                                                                                                                                                          |
| A request arrives during a run that then fails                    | It does not run at once; the back-off decides ([spaces](spaces.md#the-loop-watchts)).                                                                                         | not pinned. The test of the remembered request uses a run that succeeds.                                                                                                                                                                                |
| The user changes something while the loop is in back-off (a poke) | The poke runs a cycle 2 s later, whatever the back-off. Every change against a storage that is down makes a request. Not stated in [spaces](spaces.md) whether this is meant. | not pinned. By `schedulePoke`, which does not look at `failures`. See the findings in the report of this change.                                                                                                                                        |
| The adapter can watch                                             | A signal runs a cycle; the interval is a 5 minute safety net.                                                                                                                 | `watch.test.ts` › 'with adapter.watch a change runs a cycle and the interval is a 5-minute safety net'                                                                                                                                                  |
| Offline at a tick; hidden at a tick                               | Offline: no run, the interval tries again. Hidden: ticks are skipped, while start and poke still run; visible again, the tick runs.                                           | `watch.test.ts` › 'offline: no run, the interval tries again; hidden: ticks are skipped but start and poke run'                                                                                                                                         |
| A watch signal arrives while the page is hidden                   | Skipped.                                                                                                                                                                      | not pinned. The test above uses ticks only.                                                                                                                                                                                                             |
| A poke or `syncNow()` arrives while offline                       | No run; the interval tries again. The request is dropped, not remembered; Mixtura's `online` event calls `syncNow()` when the connection comes back.                          | not pinned, and the wiring of the `online` and `visibilitychange` events (`stock/sync-triggers.ts`) has no test at all.                                                                                                                                 |

## What these tests do not prove

- The clocks and timers are injected: a manual clock for the loop, a
  string clock for the cycle. No real browser timing, no throttled
  background tab, no real sleep or wake of a device.
- The stores are the memory store or `fake-indexeddb`. A real browser's
  IndexedDB, a real blocked upgrade and another tab's `versionchange`
  are not exercised; two tabs are never run.
- The storages are fakes that honour `ifMatch`. No real GitHub or WebDAV
  answers a cycle; the adapters are tested apart, against scripted
  responses.
- No device or page dies between a write to the storage and the write to
  the local store; the fakes cannot stop in the middle.
- The screens and the browser events (`online`, `visibilitychange`) are
  not run in these tests.
- A page that unloads is modelled as "what the store was asked to do by then"; a real
  unload, and whether Chromium commits a transaction that is already created, is not run in
  the tests. The browser check `spec-stock.mjs` does not fail on the old code locally.
- Rows marked "Reproduced with a throw-away test" were run once and not
  kept; they are findings, not tests.

## Adding a row

A fix for an ordering defect adds its row here in the same commit. The
row names the test that pins it. The commit message names the commit on
which that test fails (run it there, do not assume) and the neighbouring
cases that already passed (the controls). A test that passes without the
fix proves nothing; say so or remove it. An ordering that matters and
has no test is added as **not pinned**, with one sentence on why it is
believed to hold.
